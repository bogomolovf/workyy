## Алгоритм рефакторинга

### 1. Определить scope

Извлеки из запроса:

- **Что рефакторить** — конкретный файл, компонент, модуль, паттерн
- **Зачем** — улучшение читаемости, производительности, тестируемости, устранение дублирования
- **Ограничения** — что НЕ менять (API контракты, форматы данных)

Если scope слишком широкий — **предложи разбить** на этапы и согласуй с пользователем.

### 2. Изучить текущий код

**Обязательно перед рефакторингом:**

1. **Прочитай целиком** файл(ы) для рефакторинга
2. **Найди все использования** — Grep по экспортируемым функциям/компонентам/типам
3. **Определи зависимости** — кто импортирует этот код, от чего он зависит
4. **Проверь git blame** — понять историю изменений, не сломать недавние фиксы

**Параллелизуй:** запусти несколько Grep/Glob для одновременного поиска зависимостей.

### 3. Спланировать изменения

Создай план через tasks:

- Разбей на **атомарные шаги** (каждый шаг — проект компилируется)
- Каждый шаг можно проверить независимо
- Порядок: сначала создай новое → перенеси использования → удали старое

**Покажи план пользователю** и дождись подтверждения.

### 4. Выполнить рефакторинг

**Правила безопасного рефакторинга:**

- **Поэтапно** — каждый шаг должен оставлять проект в рабочем состоянии
- **Rename** — меняй имя во всех файлах одновременно (Grep → Edit replace_all)
- **Extract** — при извлечении компонента/хука/функции сохрани все props/параметры
- **Move** — при перемещении файла обнови все import paths
- **Inline** — при инлайнинге убедись что нет других вызовов

### 5. Проверить

1. **TypeScript**: `npx tsc --noEmit` для ВСЕХ затронутых apps/packages
2. **Lint**: `pnpm lint` для затронутых пакетов
3. **Grep**: убедись что нет сломанных импортов (`import.*from.*oldPath`)
4. **Функциональность**: убедись что поведение не изменилось
5. **Кэш**: `rm -rf apps/web/.next`

### 6. Отчёт

```
## Рефакторинг: [что сделано]

### Изменения
- [файл] — что изменилось и почему

### Что НЕ менялось
- [перечисли сохранённые API/контракты]

### Как проверить
- [шаги для ручной проверки]
```

## Что можно рефакторить

| Область                  | Что                                             | Зачем                                 |
| ------------------------ | ----------------------------------------------- | ------------------------------------- |
| `InnerBoardCanvas.tsx`   | Вынести логику в хуки `hooks/board/`            | Файл ~4500 строк, сложно поддерживать |
| Компоненты нод           | Извлечь подкомпоненты (toolbar, settings panel) | Снизить сложность                     |
| Zustand selectors        | Консолидировать дублирующиеся                   | Оптимизация ре-рендеров               |
| `any` типы               | Заменить на конкретные из `@workyy/core-domain` | Type safety                           |
| useEffect с complex deps | Упростить или разбить на несколько              | Читаемость, предотвращение багов      |
| Дублированные типы       | Перенести в `@workyy/core-domain`               | Single source of truth                |

## Красные линии — чего НЕ делать

- **Не ломать Yjs sync** — collaborative state должен работать как прежде
- **Не менять edges metadata** — `sourceHandleId`/`targetHandleId` в metadata, не на верхнем уровне
- **Не менять API контракты** — endpoint paths, request/response formats
- **Не менять payload нод** — совместимость с сохранёнными досками в БД
- **Не добавлять логику в `BoardCanvas.tsx`** — должен оставаться тонкой обёрткой
- **Не создавать новые fetch-обёртки** — используй `apiFetch` из `apiClient.ts`
- **Не менять формат коммитов** и не ломать git history
