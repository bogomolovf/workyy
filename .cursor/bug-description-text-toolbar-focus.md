# Описание бага: Прилипание фокуса к Font Family Selector в TextToolbar

## Краткое резюме

При выборе шрифта в выпадающем списке `<select>` (Font Family Selector) в тулбаре текстового узла курсор/фокус "прилипает" к этому полю, не позволяя пользователю продолжить редактирование текста в TipTap редакторе. Проблема возникает из-за того, что браузер переводит фокус на нативный `<select>` элемент при открытии выпадающего списка, и фокус не возвращается в редактор после выбора значения.

## Дефектное поведение

**Что происходит:**

1. Пользователь редактирует текст в текстовом узле (TipTap редактор)
2. Пользователь кликает на выпадающий список Font Family в тулбаре
3. Браузер открывает нативный выпадающий список `<select>`
4. Фокус переходит на `<select>` элемент
5. Пользователь выбирает шрифт из списка
6. После выбора фокус остается на `<select>` элементе
7. Пользователь не может продолжить ввод текста - курсор "прилипает" к полю выбора шрифта
8. Для продолжения редактирования пользователь должен вручную кликнуть обратно в редактор

**Ожидаемое поведение:**

- После выбора шрифта фокус должен автоматически вернуться в TipTap редактор
- Курсор/каретка должна восстановиться в той же позиции, где была до взаимодействия с тулбаром
- Пользователь должен иметь возможность продолжить ввод текста сразу после выбора шрифта
- При наведении мыши на элементы тулбара фокус и курсор НЕ должны меняться (только при реальном взаимодействии - клике)

**Фактическое поведение:**

- Фокус остается на `<select>` элементе после выбора
- Редактор теряет фокус и не восстанавливает его автоматически
- Пользователь не может продолжить ввод без ручного клика в редактор
- При наведении мыши на тулбар происходит автоматическое сохранение выделения (через `onMouseEnter`), что может вызывать нежелательные изменения фокуса

## Воспроизведение

**Шаги для воспроизведения:**

1. Откройте доску с текстовым узлом
2. Выберите текстовый узел (он должен быть выделен)
3. Кликните в редактор и начните вводить текст
4. Кликните на выпадающий список Font Family в тулбаре (над узлом)
5. Выберите любой шрифт из списка (например, "Inter" или "Arial")
6. Попробуйте продолжить ввод текста

**Условия воспроизведения:**

- Окружение: dev/prod (любое)
- Браузер: Chrome, Safari, Firefox (все основные браузеры)
- Версия: актуальная версия проекта
- Предварительные условия:
  - Текстовый узел должен быть выбран (selected)
  - Тулбар должен быть виден
  - TipTap редактор должен быть в фокусе

**Дополнительные наблюдения:**

- Проблема НЕ возникает при изменении Font Size через стрелки ↑↓
- Проблема НЕ возникает при использовании других элементов тулбара (Bold, Italic, Alignment и т.д.)
- Проблема специфична для нативного `<select>` элемента для выбора шрифта
- Проблема может также возникать при простом наведении мыши на тулбар (из-за `onMouseEnter`)

## Анализ попыток исправления

### Попытка 1: Базовое сохранение/восстановление выделения

**Что было сделано:**

- Добавлен механизм `saveSelection()` и `restoreSelection()` в `RichTextEditor`
- Использован `onMouseDownCapture` на контейнере тулбара для сохранения выделения до потери фокуса
- Добавлен `onMouseDown` с `preventDefault()` на элементы тулбара
- Использован `requestAnimationFrame` для восстановления фокуса после взаимодействия

**Файлы:**

- `apps/web/src/components/RichTextEditor.tsx` - добавлены `saveSelection` и `restoreSelection`
- `apps/web/src/components/TextNode.tsx` - добавлены `handleInteractionStart` и `handleInteractionEnd`
- `apps/web/src/components/TextToolbar.tsx` - добавлены обработчики `onMouseDownCapture` и `onMouseDown`

**Почему не сработало:**

- `preventDefault()` не предотвращает браузер от перевода фокуса на `<select>` при клике
- TipTap редактор теряет фокус до того, как срабатывает `onMouseDownCapture`
- Выделение сохраняется, но фокус все равно уходит на элемент тулбара
- `requestAnimationFrame` срабатывает слишком поздно или конфликтует с событиями браузера

**Результат:**

- Выделение сохраняется, но фокус не возвращается в редактор
- Проблема остается

## Корневая причина

### Гипотезы о корневой причине:

1. **Нативный `<select>` элемент имеет глубокую интеграцию с браузером**
   - Браузер переводит фокус на `<select>` при клике и может удерживать его даже после `onChange`
   - Нативные элементы управления имеют приоритет над программным управлением фокусом
   - Выпадающий список `<select>` может "захватывать" фокус и не отпускать его до явного закрытия

2. **TipTap редактор использует contenteditable, который имеет другую модель фокуса**
   - Contenteditable элементы теряют фокус при клике на другие элементы
   - Восстановление фокуса в contenteditable может быть сложнее, чем в обычных input/textarea
   - TipTap может иметь внутреннюю логику управления фокусом, которая конфликтует с внешними попытками

3. **Асинхронность событий браузера**
   - `onChange` срабатывает до `onBlur`
   - `requestAnimationFrame` и `requestIdleCallback` могут срабатывать слишком поздно
   - События браузера могут конфликтовать с программным управлением фокусом

4. **Автоматическое сохранение выделения при наведении**
   - `onMouseEnter` вызывает `onInteractionStart` при наведении мыши
   - Это может создавать нежелательные побочные эффекты с фокусом
   - Пользователь явно указал, что фокус не должен меняться при наведении

### Наиболее вероятная причина:

**Комбинация факторов:**

1. **Нативный `<select>` элемент "захватывает" фокус** - браузер переводит фокус на select при открытии выпадающего списка и удерживает его даже после выбора значения. Это стандартное поведение браузера, которое сложно переопределить программно.

2. **Асинхронность восстановления фокуса** - попытки восстановить фокус через `requestAnimationFrame`/`requestIdleCallback` происходят асинхронно и могут конфликтовать с событиями браузера, которые все еще обрабатывают взаимодействие с select.

3. **Автоматические изменения фокуса при наведении** - `onMouseEnter` вызывает сохранение выделения даже при простом наведении мыши, что может создавать нежелательные побочные эффекты.

## Дополнительный контекст

### Требования пользователя:

1. **"Мой курсор вообще не должен как-то меняться"** - курсор не должен меняться при наведении мыши
2. **"и фокус тоже я навожу тогда я буду взаимодействовать"** - фокус должен меняться только при реальном взаимодействии (клике), а не при наведении
3. **"если нет то не надо менять фокус приложения"** - если пользователь просто наводит мышь, фокус не должен меняться

### Технические детали:

- TipTap редактор использует `contenteditable` div
- Выделение сохраняется через `editor.state.selection` (TipTap API)
- Восстановление происходит через `editor.commands.setTextSelection()` и `editor.commands.focus()`
- Нативный `<select>` элемент не может быть легко заменен на кастомный без значительных изменений

### Логи/ошибки:

В консоли браузера нет явных ошибок. Проблема проявляется только в поведении UI.

## Рекомендации для исправления

### Предполагаемый подход:

**Вариант 1: Замена нативного `<select>` на кастомный dropdown (РЕКОМЕНДУЕТСЯ)**

- Создать кастомный компонент dropdown для выбора шрифта
- Использовать портал (React Portal) для рендеринга выпадающего списка вне DOM-дерева тулбара
- Полный контроль над фокусом - dropdown не будет "захватывать" фокус
- Можно использовать существующие компоненты из `packages/ui-kit` (если есть Popover/Dropdown)

**Вариант 2: Улучшение текущего подхода**

- Убрать `onMouseEnter` и `onMouseDownCapture` из контейнера тулбара (вызывать `onInteractionStart` только при реальном клике)
- Использовать более агрессивное восстановление фокуса сразу после `onChange` (без задержек)
- Добавить обработчик `onMouseDown` на select с немедленным `blur()` после выбора
- Использовать `useEffect` для отслеживания изменений фокуса и принудительного возврата в редактор

**Вариант 3: Использование `tabIndex={-1}` и программное открытие**

- Сделать select не фокусируемым через клавиатуру (`tabIndex={-1}`)
- Открывать выпадающий список программно через `select.click()` или `select.focus()` только при клике
- Немедленно убирать фокус после выбора через `select.blur()`

### Важные замечания:

- **Нельзя упустить:** Требование пользователя о том, что фокус не должен меняться при наведении мыши
- **Потенциальные побочные эффекты:**
  - Замена нативного select может изменить UX (но может улучшить)
  - Агрессивное управление фокусом может конфликтовать с другими обработчиками событий
  - Изменения могут повлиять на доступность (accessibility)
- **Риски исправления:**
  - Кастомный dropdown потребует больше кода и тестирования
  - Может потребоваться обновление стилей для соответствия дизайну Miro
  - Нужно убедиться, что кастомный dropdown работает на мобильных устройствах

**ВЫСОКИЙ** - проблема критически влияет на UX, пользователь не может продолжить редактирование после выбора шрифта.
