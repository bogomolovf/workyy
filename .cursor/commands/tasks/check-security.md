# Check Security

Проверка безопасности кода на наличие уязвимостей и соблюдение best practices.

## Prompt

Проверь безопасность кода на наличие уязвимостей и соблюдение best practices безопасности.

**КРИТИЧЕСКИ ВАЖНО:**

- Сохрани ВСЕ детали задачи пользователя - не теряй контекст
- Работай автономно до полного завершения проверки
- Используй codebase_search для изучения паттернов безопасности
- Выполняй множественные поиски для полного понимания

## Процесс проверки

### Шаг 1: Понимание контекста

**Сохрани ВСЕ детали:**

- Какие файлы/компоненты нужно проверить
- На что обратить особое внимание
- Какие аспекты безопасности критичны
- Любые специфические требования

### Шаг 2: Изучение паттернов безопасности

**Используй codebase_search для изучения:**

- Как обрабатываются секреты в проекте
- Как реализована валидация входных данных
- Как проверяются права доступа
- Как обрабатываются ошибки безопасности

**Примеры поисков:**

```
codebase_search: "How are API keys and secrets handled in this project?"
codebase_search: "How is input validation implemented?"
codebase_search: "How is authorization handled in API routes?"
codebase_search: "How are authentication errors handled?"
```

**Выполняй множественные поиски параллельно** для максимальной эффективности.

### Шаг 3: Детальная проверка

**Секреты:**

- ✅ Нет хардкода API keys, passwords, tokens
- ✅ Все секреты в переменных окружения
- ✅ Нет секретов в логах
- ✅ Правильное использование .env файлов
- ✅ .env файлы в .gitignore

**Валидация:**

- ✅ Валидация всех входных данных (Zod схемы)
- ✅ Валидация на клиенте и сервере
- ✅ Санитизация пользовательского ввода
- ✅ Проверка типов данных
- ✅ Валидация размеров данных (max length, etc.)

**Авторизация:**

- ✅ Проверка прав доступа перед операциями
- ✅ Использование authorizationService
- ✅ Проверка владельца ресурса
- ✅ Правильная обработка 403 ошибок
- ✅ Нет обхода проверок прав доступа

**SQL Injection:**

- ✅ Использование Prisma (автоматическая защита)
- ✅ Нет сырых SQL запросов с конкатенацией
- ✅ Prepared statements если используется сырой SQL
- ✅ Параметризованные запросы

**CORS:**

- ✅ Правильно настроены allowed origins
- ✅ Нет слишком открытых настроек (не `*` для production)
- ✅ Проверка credentials если нужно
- ✅ Правильные headers

**Rate Limiting:**

- ✅ Защита от DDoS атак
- ✅ Ограничение частоты запросов
- ✅ Защита критичных endpoints
- ✅ Правильная обработка rate limit ошибок

**Обработка ошибок:**

- ✅ Не раскрывает внутреннюю структуру
- ✅ Не показывает stack traces в production
- ✅ Правильные HTTP статус коды
- ✅ Не раскрывает чувствительную информацию
- ✅ Логирование ошибок без секретов

**Дополнительно:**

- ✅ HTTPS в production
- ✅ Безопасные cookies (httpOnly, secure, sameSite)
- ✅ Защита от XSS (санитизация вывода)
- ✅ Защита от CSRF (токены, проверка origin)
- ✅ Content Security Policy если используется
- ✅ Безопасные заголовки (X-Frame-Options, etc.)

### Шаг 4: Форматирование ответа

**Структурируй ответ:**

1. **Критические проблемы (блокеры)**
   - Уязвимости которые нужно исправить немедленно
   - Указывай конкретные файлы и строки: `filepath:line_number`
   - Объясняй почему это критично
   - Предлагай как исправить

2. **Важные замечания (нужно исправить)**
   - Проблемы безопасности которые важно исправить
   - Указывай конкретные места: `filepath:line_number`
   - Объясняй влияние на безопасность
   - Предлагай решения

3. **Рекомендации (можно улучшить)**
   - Улучшения безопасности которые не критичны но желательны
   - Объясняй преимущества
   - Предлагай конкретные улучшения

## Готов к работе

Проверь безопасность кода. Я:

1. Сохраню ВСЕ детали твоей задачи
2. Изучу паттерны безопасности через codebase_search
3. Проведу полную проверку безопасности
4. Предоставлю структурированный отчет
5. Завершу работу только когда проверка полностью завершена
