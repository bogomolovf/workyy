# Code Review

Проведение код-ревью с проверкой всех аспектов: стиль кода, безопасность, производительность, архитектура, тестирование.

## Prompt

Проведи код-ревью на основе предоставленной информации.

**КРИТИЧЕСКИ ВАЖНО:**

- Сохрани ВСЕ детали задачи пользователя - не теряй контекст
- Работай автономно до полного завершения ревью
- Используй codebase_search для изучения контекста перед ревью
- Выполняй множественные поиски для полного понимания

## Процесс код-ревью

### Шаг 1: Понимание контекста

**Сохрани ВСЕ детали от пользователя:**

- Ветка/PR для ревью
- Файлы/компоненты для проверки
- Особенности для проверки (фокус на конкретных аспектах)
- Любые специфические требования

**НЕ ТЕРЯЙ КОНТЕКСТ:** Все детали важны для правильного ревью.

### Шаг 2: Изучение кода

**Используй codebase_search для изучения:**

- Контекст изменений
- Связанные файлы и зависимости
- Как изменения вписываются в архитектуру
- Существующие паттерны в проекте
- Похожие реализации

**Примеры поисков:**

```
codebase_search: "How are similar features implemented?"
codebase_search: "What patterns are used for error handling in API routes?"
codebase_search: "How is authentication handled in similar endpoints?"
```

**Выполняй множественные поиски параллельно** для максимальной эффективности.

### Шаг 3: Проверка

**Проверь следующие аспекты:**

**Соответствие стандартам:**

- ✅ Соответствие `.cursorrules`
- ✅ TypeScript strict mode
- ✅ Правильное использование типов
- ✅ Алиасы импортов `@workyy/<package>`
- ✅ Стиль кода и форматирование
- ✅ Отсутствие console.log и debug кода
- ✅ Conventional Commits в коммитах

**Безопасность:**

- ✅ Нет хардкода секретов (API keys, passwords, tokens)
- ✅ Валидация всех входных данных (Zod схемы)
- ✅ Проверка прав доступа через authorizationService
- ✅ Защита от SQL injection (Prisma делает это автоматически)
- ✅ CORS настроен правильно
- ✅ Обработка ошибок не раскрывает чувствительную информацию

**Производительность:**

- ✅ Нет N+1 запросов к БД
- ✅ Используется select в Prisma запросах
- ✅ Мемоизация где нужно (React компоненты)
- ✅ Оптимизация запросов к БД
- ✅ Ленивая загрузка компонентов

**Качество кода:**

- ✅ Читаемость и понятность
- ✅ Правильная обработка ошибок
- ✅ Нет дублирования кода
- ✅ Следование SOLID принципам
- ✅ Правильное разделение ответственности

**Тестирование:**

- ✅ Покрытие новой функциональности тестами
- ✅ Тесты покрывают edge cases
- ✅ Тесты независимые и детерминированные
- ✅ Покрытие критичной логики минимум 80%
- ✅ Интеграционные тесты если нужно

**Архитектура:**

- ✅ Использование правильных пакетов из `packages/`
- ✅ Следование ADR из `docs/architecture/adr/`
- ✅ Соответствие паттернам из `.cursor/knowledge/patterns.md`
- ✅ Правильное использование технологий проекта
- ✅ Нет нарушения принципов SOLID

**Документация:**

- ✅ Обновлена документация API если нужно
- ✅ Обновлены ADR если архитектурные изменения
- ✅ Комментарии для сложной логики
- ✅ JSDoc для публичных функций

### Шаг 4: Форматирование ответа

**Структурируй ответ:**

1. **Критические проблемы (блокеры)**
   - Проблемы которые нужно исправить перед мерджем
   - Указывай конкретные файлы и строки: `filepath:line_number`
   - Объясняй почему это критично
   - Предлагай как исправить

2. **Важные замечания (нужно исправить)**
   - Проблемы которые важно исправить
   - Указывай конкретные места: `filepath:line_number`
   - Объясняй влияние на проект
   - Предлагай решения

3. **Предложения по улучшению (можно улучшить)**
   - Улучшения которые не критичны но желательны
   - Объясняй преимущества
   - Предлагай конкретные улучшения

4. **Положительные моменты (что хорошо)**
   - Что сделано хорошо
   - Что соответствует стандартам
   - Что можно использовать как пример

5. **Чек-лист для ревьюера**
   - Краткий список что проверить
   - Приоритеты проверок

## Формат использования

**Пользователь применяет команду и добавляет контекст:**

```
/code-review

Ветка: feature/add-board-sharing

Проверь следующее:
1. ✅ Соответствие стилю кода
2. ✅ Правильность использования типов
3. ✅ Отсутствие debug кода
4. ✅ Покрытие тестами
5. ✅ Обработка ошибок
6. ✅ Безопасность (проверка прав доступа)
7. ✅ Производительность
8. ✅ Соответствие архитектуре
9. ✅ Обновление документации
10. ✅ Conventional Commits

Фокус на:
- Правильность проверки прав доступа при шаринге
- Безопасность передачи данных между пользователями
- Обработка edge cases (удаление доски, изменение прав)

Предложи улучшения:
- Что можно улучшить?
- Есть ли потенциальные баги?
- Можно ли упростить код?
```

## Готов к работе

Проведи код-ревью на основе предоставленной информации. Я:

1. Сохраню ВСЕ детали твоей задачи
2. Изучу контекст через codebase_search
3. Проведу полное ревью всех аспектов
4. Предоставлю структурированный отчет
5. Завершу работу только когда ревью полностью завершено
