# Develop Feature

Разработка новой функциональности с изучением существующих паттернов, созданием компонентов, написанием тестов и обновлением документации.

## Prompt

Разработай новую функциональность на основе предоставленных требований.

**КРИТИЧЕСКИ ВАЖНО:**

- Сохрани ВСЕ детали задачи пользователя - не теряй контекст
- Работай автономно до полного завершения разработки
- Используй codebase_search для изучения существующих паттернов
- Планируй сложные задачи через todo_write

## Процесс разработки фичи

### Шаг 1: Понимание задачи

**Сохрани ВСЕ детали от пользователя:**

- Название фичи
- Контекст задачи (что нужно сделать)
- Где должна быть реализована (frontend/backend/оба)
- Как связано с существующей функциональностью
- Какие пользовательские сценарии покрывает
- Все требования (конкретные и измеримые)
- Технические детали
- Особые указания, ограничения, приоритеты
- Ожидаемый результат

**НЕ ТЕРЯЙ КОНТЕКСТ:** Все детали важны для правильной реализации.

### Шаг 2: Изучение существующих паттернов

**Используй codebase_search для изучения:**

- Похожие компоненты/сервисы
- Используемые паттерны
- Существующие пакеты из `packages/`
- Паттерны из `.cursor/knowledge/patterns.md`
- ADR из `docs/architecture/adr/`
- API контракты в `docs/api/openapi.yaml`

**Примеры поисков:**

```
codebase_search: "How are similar features implemented?"
codebase_search: "What patterns are used for [тип компонента]?"
codebase_search: "How is [технология] used in this project?"
```

**Выполняй множественные поиски параллельно** для максимальной эффективности.

### Шаг 3: Планирование

**Для сложных задач (3+ шага) используй todo_write:**

- Создавай атомарные задачи (≤14 слов, глагол-действие)
- Задачи должны быть высокоуровневыми (≈20 минут работы)
- НЕ включай операционные действия (linting, testing, searching)
- Отмечай задачи как completed сразу после завершения

**Пример планирования:**

```
todo_write:
1. "Create BoardList component with search and pagination" [in_progress]
2. "Add API endpoint for board search" [pending]
3. "Write tests for BoardList component" [pending]
```

### Шаг 4: Реализация

**При реализации:**

- Следуй паттернам проекта из `.cursor/knowledge/patterns.md`
- Используй существующие пакеты из `packages/` если возможно
- Используй правильные типы TypeScript (strict mode)
- Используй алиасы импортов `@workyy/<package>`
- Обрабатывай ошибки правильно
- Валидируй входные данные (Zod схемы)
- Проверяй права доступа если нужно
- Пиши тесты для нового кода
- Документируй сложную бизнес-логику

**Создавай компоненты/сервисы/роуты:**

- Frontend: Следуй паттернам Next.js App Router
- Backend: Следуй паттернам Fastify
- Используй правильные паттерны для каждого типа компонента

### Шаг 5: Тестирование

**Напиши тесты:**

- Юнит-тесты для функций и компонентов (Vitest)
- Интеграционные тесты для API если нужно
- E2E тесты для критичных сценариев если нужно (Playwright)
- Покрытие критичной логики минимум 80%

**Структура тестов:**

```typescript
import { describe, it, expect } from 'vitest';

describe('FeatureName', () => {
  it('should handle valid input', () => {
    // тест
  });
});
```

### Шаг 6: Обновление документации

**Обнови документацию:**

- API документация (`docs/api/openapi.yaml`) если новый endpoint
- ADR если архитектурные изменения
- JSDoc комментарии для публичных функций
- README если новая функциональность

### Шаг 7: Проверка

**Перед завершением:**

- Проверь что код проходит линтер: `pnpm run lint`
- Проверь что тесты проходят: `pnpm run test`
- Убедись что код соответствует стандартам
- Убедись что ВСЕ требования пользователя выполнены

## Формат использования

**Пользователь применяет команду и добавляет контекст:**

```
/develop-feature

Название фичи: Удаление доски

Контекст задачи:
Нужно добавить возможность удалять доски через API. Пользователи должны иметь возможность удалять свои доски, а админы - любые доски.

Требования:
1. Endpoint DELETE /boards/:id
2. Проверка прав доступа (только владелец или админ)
3. Каскадное удаление связанных узлов и соединений
4. Аудит событие при удалении (через auditService)
5. Возврат 404 если доска не найдена
6. Возврат 403 если нет прав доступа

Технические детали:
- Используй authorizationService для проверки прав
- Используй auditService для логирования
- Используй Prisma для каскадного удаления (onDelete: Cascade)
- Следуй паттернам из apps/realtime-server/src/routes/boards.ts
- Используй валидацию Zod для параметров

Особые указания:
- Не удаляй доски без проверки прав
- Всегда логируй удаление через auditService
- Тесты должны покрывать все сценарии (успех, 404, 403)

Ожидаемый результат:
- Endpoint DELETE /boards/:id работает корректно
- Все тесты проходят
- Документация обновлена
```

## Готов к работе

Разработай новую функциональность на основе предоставленных требований. Я:

1. Сохраню ВСЕ детали твоей задачи
2. Изучу существующие паттерны через codebase_search
3. Спланирую решение (используя todo_write для сложных задач)
4. Реализую с учетом всех требований
5. Напишу тесты
6. Обновлю документацию
7. Проверю что все работает
8. Завершу работу только когда фича полностью готова
