# Как использовать команды и агенты

## 🎯 Концепция

У нас есть два типа команд:

1. **Агентские команды** (`/developer`, `/code-reviewer`, `/test-generator`, `/migration-helper`) - активируют специализированных агентов
2. **Команды задач** (`/fix-bug`, `/develop-feature`, `/refactor`, `/code-review`, `/review-pr`, `/create-test`, `/check-architecture` и др.) - выполняют конкретные задачи

## 🔄 Пайплайн использования

### Вариант 1: Агент + Команды (Рекомендуется)

1. **Активируй агента** в новом чате:

   ```
   /code-reviewer
   ```

2. **Используй команды** в том же чате:
   ```
   /review-pr
   /check-security
   /analyze-performance
   ```

**Результат:** Агент применяет свою экспертизу к каждой команде.

### Вариант 2: Команды без агента

Просто используй команды напрямую:

```
/review-pr
/create-test
/check-architecture
```

**Результат:** Команды выполняются стандартным образом.

### Вариант 3: Агент + Описание задачи

Активируй агента и опиши задачу:

```
/code-reviewer

Проверь файл apps/realtime-server/src/routes/boards.ts:
- Фокус на обработку ошибок
- Проверь валидацию входных данных
```

## 📋 Доступные команды

### Команды для основных задач разработки ⭐

#### `/fix-bug`

Исправление багов с детальным анализом и тестами на регрессию.

**Использование:**

```
/fix-bug

Проблема:
[Описание проблемы, шаги воспроизведения, логи, стектрейсы]

Контекст:
[Файлы, компоненты, окружение]
```

#### `/develop-feature`

Разработка новой функциональности с изучением паттернов и созданием тестов.

**Использование:**

```
/develop-feature

Название фичи: [НАЗВАНИЕ]
Контекст задачи: [Что нужно сделать]
Требования: [Список требований]
...
```

#### `/refactor`

Рефакторинг кода с сохранением функциональности и улучшением читаемости.

**Использование:**

```
/refactor

Компонент: [КОМПОНЕНТ]
Цель рефакторинга: [Что улучшить]
Текущие проблемы: [Список проблем]
...
```

#### `/code-review`

Проведение код-ревью с проверкой всех аспектов.

**Использование:**

```
/code-review

Ветка: [ВЕТКА/PR]
Проверь следующее: [Список проверок]
Фокус на: [Особенности]
```

## 🤖 Агентские команды

### `/developer` ⭐ (Основной агент)

Активирует универсального Developer Agent для разработки.

**Используй для любых задач разработки:**

- Разработка новых фич
- Рефакторинг
- Исправление багов
- Создание компонентов
- Добавление API endpoints

**Пример:**

```
/developer

Создай компонент BoardList для отображения списка досок:
- Показывает все доски пользователя
- Поддерживает поиск и фильтрацию
- Использует паттерны из .cursor/knowledge/patterns.md
- Добавь тесты
```

### `/code-reviewer`

Активирует Code Reviewer Agent.

**Используй после активации:**

- `/review-pr`
- `/check-security`
- `/analyze-performance`
- `/check-architecture`
- `/suggest-improvements`

### `/test-generator`

Активирует Test Generator Agent.

**Используй после активации:**

- `/create-test`

### `/migration-helper`

Активирует Migration Helper Agent.

**Используй для:**

- Создания миграций
- Проверки миграций
- Обеспечения обратной совместимости

## 🚀 Типичные сценарии

### Сценарий 1: Исправление бага

```
/fix-bug

Проблема:
При отправке POST /boards с пустым title получаем 500 ошибку вместо 400 Bad Request.

Ожидаемое поведение: Должна возвращаться ошибка 400 с сообщением о валидации.
Фактическое поведение: Возвращается 500 Internal Server Error.

Шаги воспроизведения:
1. Отправь POST запрос на /boards с body: { "title": "", "workspaceId": "..." }
2. Получаешь 500 ошибку

Ошибки в логах:
Error: Validation failed
    at BoardService.createBoard (apps/realtime-server/src/services/boardService.ts:45)

Контекст:
- Файлы: apps/realtime-server/src/routes/boards.ts, apps/realtime-server/src/validators/boards.ts
- Окружение: DEV и PROD
```

### Сценарий 2: Разработка новой фичи

```
/develop-feature

Название фичи: Удаление доски

Контекст задачи:
Нужно добавить возможность удалять доски через API. Пользователи должны иметь возможность удалять свои доски, а админы - любые доски.

Требования:
1. Endpoint DELETE /boards/:id
2. Проверка прав доступа (только владелец или админ)
3. Каскадное удаление связанных узлов и соединений
4. Аудит событие при удалении (через auditService)
5. Возврат 404 если доска не найдена
6. Возврат 403 если нет прав доступа

Технические детали:
- Используй authorizationService для проверки прав
- Используй auditService для логирования
- Используй Prisma для каскадного удаления (onDelete: Cascade)
- Следуй паттернам из apps/realtime-server/src/routes/boards.ts
- Используй валидацию Zod для параметров

Ожидаемый результат:
- Endpoint DELETE /boards/:id работает корректно
- Все тесты проходят
- Документация обновлена
```

### Сценарий 3: Рефакторинг

```
/refactor

Компонент: BoardService

Цель рефакторинга:
Улучшить читаемость и разделить ответственность. Метод createBoard слишком большой и смешивает бизнес-логику с работой с БД.

Текущие проблемы:
1. Метод createBoard слишком большой (100+ строк)
2. Смешана бизнес-логика и работа с БД
3. Нет обработки ошибок
4. Сложно тестировать

Требования:
1. Сохрани всю функциональность (все тесты должны проходить)
2. Раздели на меньшие методы (каждый метод делает одну вещь)
3. Вынеси валидацию в отдельный метод
4. Добавь обработку ошибок
5. Следуй паттернам из .cursor/knowledge/patterns.md
```

## 💡 Best Practices

1. **Для комплексных задач** - активируй агента, используй множество команд
2. **Для быстрых задач** - используй команды напрямую
3. **Для параллельной работы** - используй несколько чатов с разными агентами
4. **Агенты можно использовать независимо** - не обязательно комбинировать с командами

## ✅ Важно

- Агенты активируются в текущем чате
- После активации агент "помнит" свою роль
- Команды можно использовать с агентом или без
- Агенты можно использовать независимо друг от друга
